Every application needs secrets: passwords for databases, keys for payment providers, tokens for other services. A common finding in security reviews is that some of these secrets live **inside the code** itself, written directly into source files or configuration.

I led the clean-up after one such review, across eleven repositories. The secrets moved out of the code into a secure cloud parameter store, and every one of them was changed ("rotated") without the website going down.

This post explains why secrets in code are a problem, and how to fix it without an outage.

## Why secrets in code are a problem

- **Anyone with access to the code has the keys.** That's usually far more people than need them.
- **History never forgets.** Code tools keep every past version. Deleting a password from today's file leaves it readable in yesterday's.
- **Changing them is painful.** If a key is written into the code, changing it means changing, reviewing and releasing code, so it rarely happens.
- **They spread.** Code gets copied into other projects, logs and screenshots.

That second point matters most: **removing a secret from the code doesn't make it safe again.** Once it has been in the code, assume it's known, and change it.

## The plan

### 1. Find every secret

Search every repository, including configuration files and past versions, for anything that looks like a password, key or token. Make a list: what it is, where it's used, and who owns the system it unlocks.

### 2. Give secrets a proper home

Store them in a secure parameter store provided by your cloud platform. It keeps values encrypted, controls exactly who and what can read them, and records every access.

### 3. Teach the apps to read from it

Each service loads its secrets from the store when it starts, instead of from its code. Two details save a lot of pain here:

- **Read secrets only after they've loaded.** If a piece of code reads its settings the instant the program starts, before the secure values have arrived, it silently falls back to defaults. That's a hard bug to spot, because everything looks fine until it isn't.
- **Check the values.** Stored settings are plain text. A typo can turn a sensible limit into "unlimited" or "zero." Validate anything that matters, and fall back to a safe default if it looks wrong.

### 4. Rotate without an outage

This is the part people worry about. The trick is **overlap**: for a short time, both the old and the new secret work.

Think of changing the locks on an office building. You don't change them at 9 a.m. and lock everyone out. You fit locks that accept both the old key and the new one, hand out new keys, wait until everyone has theirs, and only then stop accepting the old key.

For secrets, that looks like:

1. **Create the new secret** alongside the old one, so both are valid.
2. **Put the new value in the parameter store.**
3. **Restart or redeploy the services** gradually, so each picks up the new value while others keep serving traffic.
4. **Confirm everything is using the new secret.** Check logs and access records for any remaining use of the old one.
5. **Revoke the old secret.**

At no point is there a moment where a service has a secret that doesn't work.

### 5. Keep secrets out of logs

While you're there, check that nothing **prints** secrets. Logging full request details or error objects often includes passwords and access tokens without anyone noticing. Log that a token was present, never the token itself.

## Stop it happening again

Cleaning up once isn't enough if new secrets can sneak back in:

- **Automatic scanning** on every pull request, so anything that looks like a secret is flagged before it's merged.
- **A line in the review checklist:** no secrets in code, configuration or logs.
- **Easy access to the right way.** If using the parameter store is simple and documented, people use it. If it's hard, they hard-code.
- **Regular rotation.** Changing secrets on a schedule, not just after an incident, keeps the process practised and painless.

## The takeaway

Moving secrets out of code is mostly careful bookkeeping. The real skill is rotating them while customers keep shopping. If you plan for overlap, roll out gradually and check before revoking anything, it can be one of the least dramatic security projects you'll ever run. That's exactly how it should be.
